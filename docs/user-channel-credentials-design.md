# 用户自维护厂商 Key：可行性与影响评估

状态：设计评估，尚未实施。依据当前 README、用户鉴权文档、管理后台文档和实际代码。

## 1. 结论与范围

方案可行，整体影响为中高：数据库和设置页面改动相对集中，AI 调用凭证、异步任务、模型可用状态属于主要改造点。现有厂商协议实现、模型目录、用户登录、生成记录和大部分费用统计可以复用，无需重写项目。

业务分工建议：

- 平台维护厂商接入、模型目录、参数能力、接口地址、代理与超时。
- 用户维护自己在各厂商的 API Key；厂商按该 Key 对应账户的实际规则计费。
- 平台后端代用户调用厂商，因此仍需接收并安全托管用户 Key；前端不直接调用厂商。
- 生产环境缺少用户 Key 时明确提示配置，不自动借用平台 Key，也不自动返回 Mock 结果。
- Mock 仅作为明确的开发测试模式，不与用户凭证缺失混为一谈。

## 2. 文档和代码依据

| 依据 | 现状 | 对改造的意义 |
|---|---|---|
| README 的厂商模块、配置与环境变量说明 | 厂商模块已经独立，但 Key 通过全局环境变量配置 | 厂商模块可以保留，凭证来源需要替换 |
| docs/user-auth.md | 任务从登录态写入 user_id，列表、详情和费用按用户隔离 | 已有身份和归属体系，可复用到凭证管理 |
| docs/admin-api.md | 管理端与用户端使用不同认证体系 | 用户凭证管理应放用户端，管理端默认不提供原文查看功能 |
| 两个厂商的 ClientConfig | RestClient 在创建时设置包含全局 Key 的默认请求头 | 不能仅新增数据表；必须让鉴权信息改为逐次调用传入 |
| QwenLlmStrategy | 启动时使用全局 Key 创建 ChatModel | 提示词润色也需要支持按用户凭证构造或获取客户端 |
| VideoTaskWorker、ImageTaskWorker | 后台按任务执行，视频还由定时任务查询结果 | 异步执行需要通过任务关联凭证，不能依赖 HTTP 登录上下文 |

启用状态的注册用户配置个人厂商 Key 后即可生成，生成权限由账号状态、渠道接入和个人凭证决定。

## 3. 数据关系与第一期建议

用户表与凭证配置表是一对多，不建议在 t_user 增加 dashscope_key、gemini_key 等列。

第一期建议一个用户对每个厂商维护一份当前配置。例如同一用户分别拥有 DASHSCOPE、GEMINI 两条配置。这已经满足用户与 Key 配置的一对多关系，不要求同厂商支持多把 Key。

建议新增 t_user_channel_credential：

| 字段 | 用途 |
|---|---|
| id | 凭证配置 ID |
| user_id | 所属用户，由服务端登录态确定 |
| channel_code | 实际接入渠道，如 DASHSCOPE、GEMINI |
| enabled | 是否允许新任务使用 |
| current_version_id | 当前生效的密钥版本 |
| created_at、updated_at | 创建、更新时间 |

第一期对 (user_id, channel_code) 设置唯一约束。删除后重建应复用配置行或使用明确的归档设计，避免软删除与唯一约束冲突。

建议另设 t_user_channel_credential_version 保存不可变密钥版本，字段包含 id、credential_id、密文、加密主密钥版本、必要的加密参数、脱敏展示后缀、创建时间和可选验证结果。更新 Key 时新增版本并切换 current_version_id，不覆盖旧密文。

这是“用户—厂商配置一对多，配置—密钥版本一对多”。版本表用于未完成任务稳定关联凭证，不代表允许用户同时选择多把 Key。

如果以后需要同厂商多 Key，再增加名称、默认配置和选择机制，并调整唯一约束。第一期不必引入自动轮换和负载均衡。

厂商标识应与模型名称区分：QWEN 是当前大模型策略标识，其凭证渠道映射为 DASHSCOPE；万相图片、万相视频、千问在当前接入方式下可共用用户百炼 Key，不应分别创建三份重复配置。具备 Key 不代表其账户一定开通所有模型或地域权限。

## 4. 调用链改造

建议链路：

```text
用户提交 modelCode
  → 服务端识别当前用户、模型和渠道
  → 校验该用户的渠道凭证与启用状态
  → 固定凭证版本并创建任务
  → Worker 根据任务读取、解密凭证
  → 将凭证上下文传入公共策略接口
  → 厂商模块设置本次请求的鉴权信息
  → 轮询和需要鉴权的下载继续使用任务绑定版本
```

职责分配：

- aivideo-dao：新增凭证配置、版本实体及 Mapper，任务增加关联字段。
- aivideo-server：凭证 CRUD、归属校验、加解密、任务绑定和业务状态判断。
- aivideo-ai-core：定义调用凭证上下文，调整 submit、query、generate、chat 等接口。
- aivideo-ai-channel-*：消费调用上下文，处理各自的请求头、客户端和错误转换，不查询用户数据库。

共享 HTTP 连接池、代理和超时配置可以保留；包含用户身份的请求头不能通过修改共享单例客户端切换。否则并发请求可能混用 Key。Qwen 客户端可以按调用构造，后续需要缓存时应按凭证版本与模型配置隔离，并设置容量和失效机制。

凭证明文只存在于必要的后端调用过程，不写进任务请求 JSON、任务表、日志、链路追踪或前端状态持久化；凭证对象避免自动生成包含秘密的 toString。

## 5. 异步任务与 Key 生命周期

视频、图片任务至少记录生成凭证版本；开启润色时另记录润色凭证版本，两者可能不同。

| 操作 | 建议规则 |
|---|---|
| 更新 Key | 新任务使用新版本，已有任务继续绑定旧版本 |
| 停用配置 | 禁止新任务使用；已有任务按任务规则继续处理 |
| 删除配置 | 有依赖该配置的未完成任务时拒绝删除，提示先等待任务结束 |
| 旧版本清理 | 无未完成任务或下载依赖后按保留策略清理密文，保留必要审计元数据 |
| 用户在厂商侧撤销旧 Key | 无法保证旧任务继续完成，应明确标记凭证失效，禁止偷偷切换账户或重新付费提交 |
| 服务重启 | 从任务归属和凭证版本恢复调用，不依赖用户在线或线程本地状态 |

绑定版本只能保证平台不主动切换账户，不能保证厂商侧已撤销的 Key 仍可使用。不同厂商能否使用同账户新 Key 查询旧任务，需要分别核实，不作为默认假设。

Key 相关 401/403、模型无权限、额度不足、限流和网络故障应分别处理；查询异常不能一律作为普通网络异常反复重试。超时不代表厂商没有受理，也不代表没有费用，不能盲目重新提交生成。

现有 SUBMITTING 中断恢复缺口会在此次改造中继续存在，建议结合任务版本绑定补上失联处理和超时补偿。

## 6. 提示词润色的额外影响

当前润色走千问。用户只有 Gemini Key 时，可生成 Gemini 图片/视频，但不能据此调用千问。

第一期建议：润色仍走现有千问实现；用户未配置百炼 Key 时禁用润色开关并说明原因，生成能力仍可正常使用 Gemini。后台也必须验证，不能仅靠前端禁用。已配置但运行时润色失败时，可沿用使用原始提示词的降级逻辑，并保留可见的失败说明。

如果选择平台承担润色费用，需要明确列为独立的平台服务能力和费用来源，不能隐式使用平台 Key。把润色改为跟随生成厂商会涉及新增 Gemini 文本策略，属于额外功能，不是此次必需改动。

## 7. 安全、接口与用户体验

- Key 需要可逆加密以调用厂商，不能采用用户密码的 BCrypt 哈希存储方式。可使用 AES-GCM 等认证加密，加密主密钥由独立环境配置或 KMS 管理，支持主密钥版本与备份恢复。
- 凭证列表只返回渠道、启用状态、脱敏尾号和验证信息；默认不提供读取原文接口。保存新 Key 时使用 HTTPS，不放 URL，不写 localStorage，也不把脱敏占位符作为新 Key 回传。
- 所有更新、删除、验证操作都按当前用户校验归属。前端不传或不可信任 user_id；若传 credential_id，后端同时校验所属用户和渠道。
- 第一期开通平台预设接口地址。用户 Key 的区域或项目要求通过平台预设配置支持，不允许任意 baseUrl、代理或下载地址接收带密钥请求。
- 厂商响应中的错误信息需过滤，不能直接把可能含 Key 的响应、请求或异常返回给用户。管理员默认仅能看配置状态和审计，不返回密文或明文。
- Key 校验可提供显式操作，但需说明校验范围；格式正确不等于模型可调用，简单连接校验也不保证后续额度和权限。避免把付费生成作为默认校验方式。
- 使用用户 Key 后，仍需平台总并发和按用户/凭证限流，保护线程池和厂商配额。

建议新增当前用户的渠道凭证管理接口，支持列表、保存/更新、启停、删除和可选验证。前端增加“模型密钥”设置页；模型选择展示“平台已接入 / 你已配置 / 待配置”，并支持跳转设置。

模型列表的全局 available 需调整为平台支持状态与当前用户配置状态两个维度。已保存的 Key 仅能说明已配置；权限、余额和有效性仍可能在实际调用时变化。

公开的 /api/system/status 只返回环境、服务等全局信息，不能返回任何用户凭证状态。用户可用状态从受登录保护的接口获取，登录、退出和配置变更后刷新。

## 8. 费用与迁移

现有生成费用是模型单价、tokens 和配置汇率计算的应用侧估算，不是厂商账户账单。用户自有 Key 可能享有免费额度、折扣或不同项目价格，建议页面明确显示“参考费用，以厂商账单为准”。厂商用量与平台服务收费应分开表示。

上线时新增配置/版本表、任务关联字段与索引，旧数据字段允许为空。已有全局平台 Key 不能复制为每个用户的个人 Key；已有任务也不能绑定到任意用户新 Key。

优先选择停止接收新任务、等待旧任务和下载结束后切换。需要不中断迁移时，旧平台凭证只能作为明确的历史凭证来源处理，供旧任务使用；新任务不得隐式回退。历史记录、费用与图片视频资源保留。

生产启动检查应从“必须存在 DASHSCOPE_API_KEY”改为检查平台基础配置和加密主密钥；未配置个人 Key 是用户操作提示，不是阻止整个平台启动的原因。开发 Mock 入口需独立声明。

## 9. 影响程度与实施顺序

| 范围 | 程度 | 核心工作 |
|---|---|---|
| 数据库、DAO | 中 | 凭证配置/版本表，任务关联字段，归属查询与迁移 |
| AI 核心、厂商模块 | 高 | 全局凭证改为逐次调用凭证，覆盖生成、查询、润色及鉴权下载 |
| 任务编排 | 高 | 固定凭证版本、异步恢复、失效和删除语义 |
| 模型/系统状态接口 | 中 | 区分平台能力和用户配置，移除全局 Key 判定 |
| 用户前端 | 中 | 密钥设置、配置引导、润色可用性和状态刷新 |
| 管理前后端 | 低 | 首期可不增加密钥管理，仅调整费用文案和必要元数据 |
| 运维与安全 | 中高 | 加密主密钥、权限、日志过滤、迁移、备份与轮换 |
| 模型参数、协议、生成记录 | 低 | 现有主体逻辑可复用 |

建议分为三步交付：先完成凭证存储与用户管理页面；再完成三类模型调用和任务版本绑定；最后完成状态体验、历史迁移和回归验证。凭证未完整接入调用链前不应作为生产功能上线。

必须覆盖的验证包括：两个用户同厂商并发不串 Key；跨用户 CRUD/验证被拒绝；同用户跨厂商隔离；图片、视频、千问、轮询、受保护下载全部使用正确凭证；更新 Key 后旧任务继续使用原版本；删除与重启规则可预测；权限/额度/限流故障准确反馈；前端响应、异常日志与数据库任务字段无明文泄露；历史任务与费用查询正常。

## 10. 推荐第一期业务边界

1. 每用户每厂商一份当前配置，支持更新和停用。
2. 平台维护厂商和接口地址，用户只维护 Key。
3. 用户任务只用该用户 Key，生产缺失时明确提示配置。
4. 凭证加密保存、列表只展示脱敏信息，默认不支持原文回显。
5. 任务绑定不可变凭证版本，删除不能影响未完成任务。
6. 千问润色需要用户自己的百炼 Key；未配置则不启用润色。
7. 费用作为参考统计，实际扣费以厂商账单为准。

以上为建议方案，不代表同厂商多 Key、平台代付、用户自定义中转地址或自动轮换已被确认为业务需求。
